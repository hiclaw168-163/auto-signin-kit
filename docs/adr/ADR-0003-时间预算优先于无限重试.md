# ADR-0003-请求层带时间预算,预算优先于"再多试一次"

- **状态**: 已接受并实现
- **日期**: 2026-10
- **关联**: SPEC-02 §httpclient · SPEC-03 §5 预算表 · 各域 api.parse_budget

## 背景

本类工具跑在 Windows 计划任务里,`ExecutionTimeLimit`(如 PT5M/PT10M)到点
**直接强杀**,进程没有任何机会写日志。盲目"再重试一次"的网络层在这种宿主下
必然偶尔导致"无痕失败"——真实发生过。

## 决策

`core/httpclient.Budget(seconds)`(单调时钟,不受系统改时间影响)贯穿每次请求:

1. 每次请求前查 `remaining() <= 1` → 直接 `BUDGET_OUT`(-2,不发请求);
2. 重试决策与 budgets 联动: 退避表内每一步都要满足
   `remaining() > delay + timeout`,否则放弃重试如实返回;
3. 单请求超时收缩为 `min(timeout, remaining())`;
4. 各域 `parse_budget` **绝不抛异常**: 环境变量非法回落默认、越界夹上限,
   只给 `config_warning`——配置坏了也要能出结果。

预算上限由调用方(域)声明,与计划任务执行上限对齐:

| 域/场景 | 默认 | 上限 |
|---------|------|------|
| workbuddy 签到 | 420 | 540 |
| workbuddy 轮询 | 180 | 240 |
| qoder 任意 | 240 | 240 |
| trae 任意 | 240 | 240 |

## 结果与代价

- 结果: 最坏情况输出 `{"result":"TIMEOUT",…}` + 日志,而不是被系统无声击毙。
- 代价: 手动管理预算会忘——所以 `call()` 是唯一入口,
  `NO_NETWORK=0`/`BUDGET_OUT=-2` 是显式伪状态码,调用方必须显式分支处理。
- 重试分桶(`RetryPolicy`)是补充手段而非替代: 冷启动"前几次网络不可达、
  之后转 5xx"的场景,单一全局重试计数会让 5xx 一次都摸不到(实测经验)。
